Manus关于Agent上下文工程的实践经验分享, 2025
Manus关于Agent上下文工程的实践经验分享, 2025今天我们来聊聊 AI Agent 开发中的一个硬核话题——上下文工程。Manus 一直是我们构建 AI Agent 道路上的好老师。去年 10 月份，Manus 的首席科学家 Peak Ji（季逸超）和 LangChain 的创始工程师 Lance 做了一次深度交流。他们不仅梳理了上下文工程的概念，还分享了很多 Manus 在实战中的独家秘籍，特别是关于如何构建生产级 AI Agent 的那些前沿实践和核心开发哲学。
那么，首先我们得弄清楚一个概念，什么是上下文工程？简单来说，它是一门把“恰到好处”的信息填进模型上下文窗口的艺术和科学，目的是确保模型能做出正确的下一步决策。这跟我们平时说的“提示工程”可大不一样。提示工程通常关注的是单次交互的优化，而上下文工程的核心在于管理一个动态变化的上下文环境。
为什么要管理这个环境呢？因为 AI Agent 面临着两个非常棘手的核心悖论。
第一个叫“上下文爆炸”。你想啊，Agent 为了完成任务，得在一个循环里不断地自主调用工具。每次调用的结果都要追加到聊天历史里。任务稍微复杂一点，比如需要调用个 50 次工具，这消息列表就跟滚雪球一样，无限制地增长，瞬间就能把模型的上下文窗口给撑爆了。
第二个叫“上下文腐烂”。研究和实践都表明，当塞给模型的上下文太长时，模型的脑子就不好使了。它的推理能力会减弱，开始出现重复行为，决策质量下降，反应也变慢。这直接损害了 Agent 的核心能力。
你看，这就形成了一个根本性的矛盾：Agent 想要干好活，依赖丰富的历史上下文；但上下文一多，又直接侵蚀了它的性能。所以，上下文工程就成了通过一系列精巧的技术来管理信息流，推动 AI Agent 走向实用化和稳定运行的基石。
为了搞定这些挑战，业界现在主要涌现出了五大流派，或者说五个工具箱里的工具。通常大家在生产级应用中是把它们组合起来用的。
第一招叫“上下文卸载”。就是把暂时用不着的信息从实时窗口里拿出来，存到外部的文件系统里，等需要的时候再去访问。第二招叫“上下文缩减”。简单粗暴，就是通过总结或者压缩，直接减少上下文里的信息量，或者剪掉那些旧的、不再相关的历史。第三招是“上下文检索”。不再一股脑把历史都塞给模型，而是变被动为主动，让模型按需去检索，比如建立向量索引，或者让 Agent 用 grep 这样的工具去文件系统里搜。第四招是“上下文隔离”。把大任务拆给多个子 Agent，每个子 Agent 只需要关注自己那一部分独立的、更小的上下文。第五招叫“上下文缓存”。利用 KV 缓存技术，来降低成本和延迟。
说到这儿，Manus AI 他们家有一些特别独到的做法，对这些技术进行了深化和创新，我觉得特别值得大家参考。
首先是关于“上下文缩减”，Manus 采用了一套“可逆紧凑化”配合“结构化总结”的策略。他们先是测出了一个“腐烂前阈值”，比如 128k 到 200k tokens。只要没到这个线，模型表现就是稳的。一旦快到这个线了，他们先做“紧凑化”。这是什么意思呢？比如 Agent 写了一个文件，原来的记录里有完整的文件内容。但其实只要知道文件路径，内容是可以恢复的。所以他们就把那个长长的 content 字段删掉。这样做的好处是信息没丢，随时能还原。通常他们只压缩最旧的那 50% 的历史，最新的还是保留原样作为 few-shot 示例，防止模型学坏了，以为只能输出简略版。如果紧凑化还不够腾空间，他们才会动用“总结”这一招。但他们不做那种自由发挥的总结，而是让模型填一个预定义的结构化表格（Schema），比如明确填好“修改了哪些文件”、“用户的目标是啥”，确保关键信息不丢。
再来说说工具过载的问题。我们知道工具给多了（比如超过 30 个），模型容易晕，KV 缓存也容易失效。Manus 设计了一个创新的“三层动作空间”来解决这个问题。第一层，只有 10 到 20 个最核心的原子函数，比如 read_file、write_file。这些是固定的，正交的，对缓存很友好。第二层，是沙箱实用程序。就是在定制的 Linux 虚拟机沙箱里预装好的命令行工具，比如格式转换器、语音识别。第三层，是包和 API。Agent 可以自己写 Python 脚本来调用第三方的 API 或者自定义库。这就很有意思了，在模型眼里，它始终只是在用第一层那几个简单的原子函数跟世界交互，但通过后两层，它的能力其实是被无限扩展的。
关于多 Agent 协作，Manus 借鉴了 Go 语言社区的智慧，清晰地划分了两种模式。一种叫“通过通信共享内存”。主 Agent 给子 Agent 发个具体的指令提示，子 Agent 在一个仅包含该指令的隔离上下文中干活。这种方式高效、成本低，适合任务明确的场景。另一种叫“通过共享内存通信”。这就比较奢侈了，子 Agent 能看到主 Agent 完整的聊天历史。这适合那种交织的、需要了解全貌的复杂任务。而且为了防止沟通出岔子，Manus 引入了 Schema 作为“契约”。主 Agent 发任务前先定好输出格式，子 Agent 通过一个特殊的 submit_result 工具，严格按这个格式交作业，保证信息不走样。
聊了这么多技术细节，最后我们来升华一下，看看 Manus 在开发中总结出的核心哲学。他们发现，产品性能的最大飞跃往往不是来自增加更复杂的上下文管理技术，而是来自简化架构。他们的核心理念是“少构建，多理解”。工程的目标是让大语言模型的工作变得更简单，而不是更困难。开发者应该多花时间去理解模型本身的行为和局限，而不是盲目堆砌工程技术来约束它。
最后还有几条非常实用的战略建议：第一，选模型要灵活。如果你的 Agent 应用输入远大于输出，KV 缓存就是关键。这时候大厂的闭源模型拥有成熟的全球分布式缓存，可能比自己部署开源模型更划算。而且要学会“看菜吃饭”，比如编程任务用 Claude，多模态任务用 Gemini。第二，架构要有“未来性”。怎么判断你的架构好不好？试着从弱模型切换到强模型。如果性能有显著提升，说明你的架构是好的，能适应未来的发展。第三，关于长期记忆，采用“用户在环”策略。不要想当然地替用户记东西，通过显式的系统让用户确认是否要存为长期记忆。第四，安全是底线。要把 Agent 关在沙箱里严格控制信息外泄，所有敏感操作（比如执行代码、操作浏览器）都必须让人类亲自确认。
