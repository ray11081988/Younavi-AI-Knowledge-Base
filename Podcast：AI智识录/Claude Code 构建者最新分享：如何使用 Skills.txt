Claude Code 构建者最新分享：如何使用 Skills
这篇文章翻译自 Claude Code 团队核心成员 Thariq Shihipar 最近在 X 上发表的经验分享，原文标题为Lessons from Building Claude Code: How We Use Skills.
在 Anthropic 内部已经有数百个 Skills 在日常开发中被高频使用，作为 Claude Code 的构建者，Thariq 总结了一套写好 Skill 的最佳实践，比如如何利用文件夹结构、如何写“避坑指南”，以及团队内部该怎么分享和管理这些工具。
如果你在研究 Skill 机制并且想在 Agent 中用好它，这篇来自官方的一手经验非常有参考价值。它没有复杂的大词，全是可以直接借鉴的实用技巧。
以下是全文翻译：
Skills（技能）已经成为 Claude Code 中最常用的扩展点之一。它们灵活、易于创建，并且分发简单。
但这种灵活性也让我们很难弄清楚什么样的方式效果最好。哪些类型的 Skills 值得制作？编写一个优秀 Skill 的秘诀是什么？什么时候应该与他人分享？
在 Anthropic，我们一直在 Claude Code 中广泛使用 Skills，目前有数百个正在活跃使用中。以下是我们利用 Skills 加速开发所学到的经验教训。
我们经常听到关于 Skills 的一个常见误解是，它们“只是 markdown 文件”，但 Skills 最有趣的部分在于它们不仅仅是文本文件。它们是包含脚本、静态资源、数据等的文件夹，Agent（智能体）可以发现、探索并操作它们。
我们发现，Claude Code 中一些最有趣的 Skills 正是创造性地利用了这些配置选项和文件夹结构。
在整理了我们所有的 Skills 之后，我们注意到它们聚集在几个反复出现的类别中。最好的 Skills 都能清晰地归入其中一类；而那些容易引起混淆的往往跨越了多个类别。这并不是一份最终的清单，但它可以作为一个很好的参考，帮你思考你的组织内部是否遗漏了某些类型的 Skills。


一旦你决定了要制作的 Skill，该如何编写它呢？以下是我们发现的一些最佳实践、提示和技巧。
我们最近还发布了 Skill Creator（技能创建器），让在 Claude Code 中创建 Skills 变得更加容易。
Claude Code 非常了解你的代码库，而且 Claude 在编码方面拥有海量知识，包括许多默认的观点倾向。如果你要发布一个主要关于知识的 Skill，尽量将重点放在那些能打破 Claude 固有思维模式的信息上。

任何 Skill 中最有价值（highest-signal）的内容就是“避坑指南（Gotchas）”部分。这些部分应该基于 Claude 在使用你的 Skill 时遇到的常见失败点来构建。理想情况下，你应该随着时间的推移更新你的 Skill 以捕捉这些坑点。

正如我们之前所说，Skill 是一个文件夹，而不仅仅是一个 markdown 文件。你应该将整个文件系统视为一种上下文工程（context engineering）和渐进式信息披露（progressive disclosure）的形式。告诉 Claude 你的 Skill 中有哪些文件，它会在适当的时候去读取它们。
渐进式披露最简单的形式就是指向其他供 Claude 使用的 markdown 文件。例如，你可以将详细的函数签名和使用示例拆分到 references/api.md 中。
另一个例子：如果你的最终输出是一个 markdown 文件，你可能会在 assets/ 中包含一个模板文件供其复制和使用。
你可以拥有存放参考文献、脚本、示例等的文件夹，这些都有助于 Claude 更高效地工作。

当 Claude Code 开启一个会话时，它会构建一个包含每个可用 Skill 及其描述的列表。这个列表就是 Claude 用来扫描并决定“是否有适合此请求的 Skill？”的依据。这意味着描述字段不仅仅是一个摘要——它更是关于何时触发此 Skill 的说明。


某些 Skills 可以通过在其内部存储数据来包含一种记忆形式。你可以将数据存储在简单如仅追加（append-only）的文本日志文件或 JSON 文件中，也可以复杂如 SQLite 数据库中。
例如，一个 standup-post（站会汇报）Skill 可能会保存一个 standups.log，记录它写过的每一篇汇报，这意味着下次你运行它时，Claude 会读取它自己的历史记录，并能分辨出与昨天相比发生了什么变化。
当你升级 Skill 时，存储在 Skill 目录中的数据可能会被删除，因此你应该将其存储在一个稳定的文件夹中。目前我们为每个插件提供 ${CLAUDE_PLUGIN_DATA} 作为一个稳定的文件夹来存储数据。

Skills 可以包含仅在调用该 Skill 时才激活的钩子（hooks），并持续整个会话期间。将此用于那些你不想一直运行，但在特定时候极其有用的、具有主观倾向性的钩子。
例如：
•   /careful —— 通过 Bash 上的 PreToolUse 匹配器拦截 rm -rf、DROP TABLE、force-push、kubectl delete 命令。你只在确认自己正在操作生产环境（prod）时才需要它——如果一直开着，你会疯掉的。
•   /freeze —— 拦截任何不在特定目录下的 Edit（编辑）/Write（写入）操作。这非常有用。
•   在调试时：“我想添加日志，但我总是意外地‘修复’了不相关的部分”。
Skills 最大的好处之一是你可以与团队其他成员分享它们。
你有两种方式可以与他人分享 Skills：
•   将你的 Skills 提交到你的代码仓库中（在 ./.claude/skills 目录下）。
•   制作一个插件，并设立一个 Claude Code 插件市场，用户可以在那里上传和安装插件。
对于在相对较少代码仓库上工作的小型团队，将 Skills 提交到仓库中效果很好。但是，每个提交的 Skill 也会给模型稍微增加一点上下文。随着规模的扩大，内部插件市场允许你分发 Skills 并让你的团队决定安装哪些。
你如何决定哪些 Skills 可以进入市场？人们又该如何提交它们？
我们并没有一个专门的中心化团队来做决定；相反，我们试图有机地寻找最实用的 Skills。如果你有一个希望大家试用的 Skill，你可以将其上传到 GitHub 中的沙盒（sandbox）文件夹，并在 Slack 或其他论坛中引导人们去尝试。
一旦某个 Skill 获得了足够的关注（这由 Skill 的所有者来决定），他们就可以提交一个 PR 将其移入市场。
需要提醒的是，创建糟糕或冗余的 Skills 是很容易的，因此确保在发布前有某种审核机制非常重要。
你可能会希望拥有相互依赖的 Skills。例如，你可能有一个上传文件的文件上传 Skill，以及一个生成 CSV 文件并将其上传的 CSV 生成 Skill。这种依赖管理目前尚未原生内置于市场或 Skills 中，但你只需通过名称引用其他 Skills，如果模型安装了它们，它就会自动调用。
为了了解某个 Skill 的表现，我们使用了一个 PreToolUse 钩子，这使我们能够记录公司内部的 Skill 使用情况。这意味着我们可以发现哪些 Skills 很受欢迎，或者哪些 Skills 的触发次数低于预期。
对于 Agent 而言，Skills 强大得令人难以置信，且十分灵活，但目前仍处于早期阶段，我们都在探索如何最好地利用它们。
与其把这当成一份终极指南，不如把它看作是一个包含有效技巧的大礼包。了解 Skills 最好的方式就是开始动手、尝试，然后看看什么对你有效。我们大多数的 Skills 刚开始时都只有短短几行代码和一个坑点记录，随着 Claude 遇到新的边缘情况（edge cases），大家不断地往里添加内容，它们才变得越来越好。
