Anthropic（Claude）官方：How Skills compares to prompts, Projects, MCP, and subagents
今天我们要聊的话题是今年在上下文工程领域各种新方法、概念的更新速度让人眼花缭乱的 Claude。以前我们用 AI，好像只要学会怎么写“提示词”（Prompts）就够了，只要你会说话，只要你能把问题描述清楚，AI 就能给你干活。但是现在呢？你打开 Claude 的界面，或者看它的开发者文档，你会发现突然多了一大堆新名词：什么 Projects（项目）、Artifacts（画布），最近又出了个叫 Skills（技能）的东西，还有什么 Subagents（子智能体）、MCP（模型上下文协议）……
我听到很多朋友在抱怨：“天哪，我不就是想让 AI 帮我写个周报、修个 Bug 吗？为什么我要搞懂这么多复杂的概念？这些东西到底有什么区别？我什么时候该用哪个？”今天的节目就想帮大家彻底理清这个思路。我们要聊的这篇文章，来自 Claude 的官方博客，叫《Skills explained: How Skills compares to prompts, Projects, MCP, and subagents》（技能详解：技能与提示词、项目、MCP 及子智能体的比较）。
这篇文章不仅仅是在解释新功能，它其实是在向我们展示一张地图——一张如何构建高效 AI 工作流的地图。不管你是普通的日常用户，还是正在开发复杂 AI 应用的开发者，听完这期节目，你脑子里会有一个无比清晰的图景：在 Claude 的这个“大厨房”里，每一件工具到底是干什么用的，以及它们怎么组合在一起，能做出一桌满汉全席。
好，让我们开始吧。
首先，我们要从最基础、也是大家最熟悉的那个概念讲起——提示词（Prompts）。
虽然大家天天都在用，但如果让你给“提示词”下一个精准的定义，你会怎么说？
在 Claude 的这篇文章里，它给了一个非常精准的描述：提示词，是你用自然语言给 Claude 的、当下的、一次性的指令。
请注意这里面的几个关键词：当下的（In the moment）、短暂的（Ephemeral）、反应式的（Reactive）。它的特点是快，是即兴的。你只需要他在此时此刻，完成这一个具体的动作。
在 Claude 的使用场景里，什么时候用提示词最合适呢？
文章里列举了几个典型场景：
第一，一次性的请求。比如，“帮我总结这篇 5000 字的文章”，或者“给我讲个笑话”。这事儿干完就完了，不需要后续。
第二，对话式的微调。比如 Claude 给你写了一段文案，你觉得太严肃了，你跟它说：“嘿，把语气改得活泼一点，加几个 Emoji。” 这也是提示词，你在实时调整它的输出。
第三，提供即时的背景信息。比如你直接把一段乱七八糟的数据贴给它，说：“分析一下这些数据，告诉我有什么趋势。”
提示词就像是我们和 AI 之间最原始、最直接的沟通桥梁。它的优势在于灵活。你想在这个对话里聊莎士比亚，下一个对话里聊量子力学，完全没问题，因为它不“记仇”，也不“记事儿”，每一个新的对话框（Chat）都是一张白纸。
但是！重点来了，这种“白纸”特性，也是它最大的局限性。
我相信大家都有过这样的经历：你花了半个小时，教会了 Claude 怎么模仿你们公司的行文风格。你告诉它：“标题要用三号黑体，每段开头要空两格，语气要既专业又亲切，不要用那些文绉绉的成语……” 终于，它学会了，写出了一篇完美的通告。
然后，第二天，你关掉电脑，重新打开一个新的 Chat，想让它写第二篇通告。
你发现，它又变回了那个“出厂设置”的 Claude。你之前教它的所有规矩，它全忘了。你不得不把昨天那段几百字的要求，重新复制粘贴一遍。
这就是所谓的“金鱼记忆”。提示词是不持久的，它只活在当前的对话框里。一旦对话结束，或者你开启了新对话，一切归零。
所以，如果你的工作流里充满了“重复劳动”，如果你发现自己每天都在把同一段 prompt 复制来复制去，那就说明，你该升级你的工具了。
这就引出了我们的下一个主角——项目（Projects）。
在技术层面上，Projects 是一个独立的工作区。它最核心的能力是提供持久的上下文。你可以往这个 Project 里上传各种文档、代码、文本文件。目前 Claude 的 Project 支持大概 20 万 token 的上下文窗口，这相当于一本厚厚的小说。而且当你在这个 Project 里的知识库越来越大，快要超过那个限制的时候，Claude 会自动开启一种叫 RAG（检索增强生成）的模式，把容量再扩大 10 倍。这意味着你可以把整整几十万字甚至上百万字的资料塞给它。
那么，什么时候该用 Projects 呢？
当你需要背景知识（Background Knowledge）贯穿整个工作流的时候。
举个例子：假设你在负责公司第四季度的产品发布会。
如果用普通的 Chat（提示词模式），你每次让 Claude 写个宣传文案，都得先把产品说明书发给它一遍。
但是如果你建了一个叫“Q4 产品发布”的 Project：
1.   你可以把市场调研报告、竞品分析、产品详细规格书、过往成功的文案案例，全部扔进去。
2.   然后，你在这个 Project 里开启任何一个新的对话，Claude 都会自动“读”过这些材料。
3.   你只需要说：“给这次发布会写个开场白。”
4.   它立刻就能写出来，而且能精准地引用到规格书里的参数，还能模仿过往案例的语气，完全不需要你再废话。
Projects 就像是给 Claude 装了一个“外挂大脑”。它特别适合团队协作（如果你用的是 Team 版），或者你需要把不同的工作场景隔离开的时候。
比如，你可以有一个 Project 叫“写代码助手”，里面放满了你们公司的代码规范和 API 文档；
另一个 Project 叫“自媒体运营”，里面放满了你的爆款文章和用户画像。
你在“写代码”的房间里，它就是个严谨的程序员；你走进“自媒体”的房间，它就是个懂流量的营销号小编。
但是，这时候有朋友可能会问了：“好吧，Projects 解决了‘资料’的问题，它让 Claude 知道了‘我是谁’、‘我有什么资料’。但是，它并没有解决‘怎么做’的问题啊？”
没错，这是一个非常敏锐的观察。
Projects 能够提供知识（Knowledge），但它不一定能高效地提供技能（Skills）。
比如，你知道你们公司的代码规范（这是知识），和你能不能每次都精准地执行一套复杂的代码审查流程（这是技能），是两码事。
你可以在 Project 里放一份文档说：“我们要进行安全审查。” Claude 读了，它知道要审查。但是，具体第一步查什么？第二步查什么？怎么查 SQL 注入？怎么查 XSS 攻击？如果每次都要它凭空去想这个流程，它可能会发挥不稳定，有时候查得细，有时候查得粗。
这时候，我们需要一本“操作手册”，我们需要把这种“流程性的知识”固化下来。
于是，Claude 家族里最强大的新成员登场了——技能（Skills）。
技能（Skills），是这次官方博客重点介绍，也是最容易让人混淆的一个概念。
很多人会问：“既然我已经有了 Project，我在 Project 的自定义指令（Custom Instructions）里写上‘你是一个安全专家’，不就行了吗？为什么还需要 Skills？”
这里的区别非常微妙，但非常关键。
文章里用了一个特别好的比喻：
Projects（项目） 像是给 Claude 提供了一个图书馆。它拥有了所有的书，所有的背景资料。
Skills（技能） 像是给 Claude 发了一本专门的培训手册，或者说是给它装了一个“特种兵技能包”。
Skills 本质上是包含了一组指令、脚本甚至是一些辅助资源（比如 Excel 模板）的文件夹。它不仅仅是告诉 Claude “这是什么”，而是手把手教 Claude “这事儿该怎么干”。
而且，Skills 有一个非常酷的技术特性，叫做动态加载和渐进式披露（Progressive Disclosure）。
这是什么意思呢？
想象一下，你有一个超级全能的 AI 员工。如果你一开始就把公司所有的 1000 个办事流程——从怎么报销发票，到怎么修服务器，再到怎么写公关稿——全部一股脑塞进它的脑子里（也就是塞进上下文窗口），那它不仅会变慢，而且可能会“精神错乱”，搞混不同流程的步骤。
Skills 解决了这个问题。
当你创建了一堆 Skills 的时候，比如一个叫“Excel 数据分析”，一个叫“品牌设计规范”，一个叫“代码安全审查”。
Claude 一开始并不会把这些所有内容的细节都读进去。它只读取每个 Skill 的“封面”——也就是它的元数据（Metadata），这只占很小很小的内存（大概 100 个 token）。
当你在对话中突然说：“帮我分析一下这个 Excel 表格。”
Claude 脑子里的“雷达”会瞬间扫描：“哎？现在的需求是处理 Excel。让我看看我的技能包里有没有相关的……有了！‘Excel 数据分析’技能！”
只有在这一刻，它才会把那个 Skill 文件夹里的详细指令、脚本、模板，“哗”地一下加载进来。
任务做完之后，在这个对话的其他部分，如果不需要了，它就不会一直占着内存干扰判断。
这种机制让 Claude 可以变得非常专精，同时又保持轻量。
那么，什么时候该用 Skills 呢？
当你需要 Claude 稳定地、重复地、高效地执行某项专门任务的时候。
文章里给了三个非常典型的场景：
1.   组织工作流：比如“品牌指南”。你把公司的配色方案、Logo 使用规范、字体要求做成一个 Skill。以后无论谁用 Claude 做 PPT，只要触发这个 Skill，做出来的东西绝对符合公司标准，不用每个人都去背一遍 VI 手册。
2.   领域专长：比如“高级 Excel 技巧”。你可能不会写复杂的 VLOOKUP 或者宏，但你可以把这些高阶用法做成 Skill。当需要处理数据时，Claude 就变成了一个 Excel 大师。
3.   个人偏好：比如你有一个独特的“卡片笔记法”写作流程。你可以把它封装成 Skill，每次写读书笔记时自动调用。
让我们来做一个具体的对比，彻底分清 Project 和 Skill。
假设你要进行一次“Q4 产品发布”。
Project 里装的是：这次发布会的产品参数、竞品报告、目标用户画像。（这是背景，是Context）
Skill 里装的是：你们团队的“爆款文案写作法”——第一步怎么写标题，第二步怎么埋痛点，第三步怎么给方案。（这是方法，是Procedure）
如果你的“爆款文案写作法”只用在这次 Q4 发布会上，那你可以把它写在 Project 的指令里，没问题。
但是！如果到了 Q1、Q2、Q3 发布会，你都要用这套写作法，那你就不应该把它锁在 Q4 的 Project 里。你应该把它提取出来，做成一个独立的 Skill。这样，无论你在哪个 Project 里工作，你都可以随时召唤这个“文案写作技能”。
所以，简单总结一下：Project 是关于“在这儿”（Where & What），而 Skill 是关于“怎么做”（How）。 Project 是为了隔离不同的工作任务，而 Skill 是为了复用通用的能力。
听到这里，是不是感觉思路清晰了很多？
但这还不是全部。Claude 的生态里还有两个更硬核的角色：子智能体（Subagents） 和 MCP（模型上下文协议）。
如果说 Skills 是让 Claude 学会了某种技能，变成了“专家”，那么 子智能体（Subagents） 就是让 Claude 变成了“包工头”。
在复杂的任务中，我们有时候不希望所有的活儿都让同一个 AI 来干。为什么？因为“术业有专攻”，而且为了安全和效率。
子智能体，顾名思义，就是在主智能体（Main Agent）下面干活的小弟。它们有自己独立的上下文窗口，有自己特定的系统提示词，最重要的是——它们有特定的工具权限。
这是 Subagents 和 Skills 最大的区别。Skill 只是教 Claude 怎么做，它是在同一个对话里运行的。而 Subagent 像是一个独立运行的小程序，它可以被限制权限。
文章里举了一个非常精彩的例子：代码审查。
假设你在用 Claude 开发一个软件。你给了 Claude 读写代码的权限。这很方便，但也很危险。万一 Claude 抽风了，把你的核心代码删了怎么办？或者它为了修一个 Bug，引入了一个严重的安全漏洞怎么办？
这时候，你可以设计一个专门的“代码审查员”子智能体（Code-reviewer Subagent）。
你可以给这个子智能体配置极高的安全标准，但是——只给它“读”代码的权限，不给它“写”代码的权限。
工作流程就变成了这样：
1.   你（或者主智能体）写了一段新代码。
2.   主智能体自动把这段代码扔给“代码审查员”子智能体。
3.   审查员拿着它的放大镜（专门的安全审查 Prompt），死抠每一个细节。因为它没有写权限，所以你不用担心它会手滑改坏东西。
4.   审查员把审查结果（比如“第 5 行有漏洞”）反馈给主智能体。
5.   主智能体再去修改。
这就是子智能体的核心价值：任务隔离（Task Isolation）和权限控制（Tool Restriction）。
它们特别适合处理那些需要高度专业化、或者需要并行处理、或者有安全风险的任务。你可以想象成，主智能体是项目经理，它手里养了一群专门干脏活累活、或者专门干高精尖活儿的实习生和专家。
好了，我们有了临时的指令（Prompts），有了持久的资料库（Projects），有了专业的技能包（Skills），还有了分工明确的团队（Subagents）。
看起来很完美了？
不，还有一个致命的问题。直到目前为止，我们聊的所有东西，都发生在 Claude 这个“大模型”的脑子里，或者是我们要手动上传文件给它。
但是，你的真实工作数据在哪儿？
它们在你的 Google Drive 里，在公司的 Slack 聊天记录里，在 GitHub 的代码仓库里，在那个古老的 SQL 数据库里。
如果每次都要把这些数据下载下来，再上传给 Claude，那这根本称不上“智能”，只能叫“人工搬运智能”。
于是，MCP（Model Context Protocol，模型上下文协议） 诞生了。
这是 Claude 试图建立行业标准的一个野心勃勃的举动。简单来说，MCP 就是一个通用插头（Universal Adapter）。
在以前，如果你想让 AI 连上你的数据库，你得专门写一段复杂的代码接口。想连 Google Drive？又要写一套。想连 Slack？还得写一套。
MCP 说：别这么麻烦了。咱们定个标准吧。
只要你的数据源（比如 Google Drive）装上了 MCP 的“插座”（MCP Server），Claude 这个“插头”（MCP Client）就能直接插上去。
MCP 的作用是连接（Connectivity）。
通过 MCP，Claude 可以：
1.   直接去你的 Google Drive 里搜索文件。
2.   直接读取 GitHub 上的最新代码。
3.   直接查询你公司的 CRM 系统里的客户数据。
而且，这种连接是实时的。你 Google Drive 里的文件刚才改了，Claude 下一秒读到的就是改过的版本，不需要你重新上传。
回到我们要区分的重点：MCP 和 Skills 有什么区别？
这俩很容易混。因为它们看起来都在增强 Claude 的能力。
区别在于：MCP 负责“拿到数据”，Skills 负责“处理数据”。
文章里那个例子特别生动：
如果你想让 Claude 帮你分析数据库里的销售数据。
MCP 是那把钥匙，它让 Claude 能打开数据库的大门，看到里面的数据。
Skills 是那个分析师的脑子，它教 Claude：“拿到数据后，你要先按日期排序，然后计算同比增长率，最后生成一个饼图。”
如果你只教了 Skill（怎么分析），但没有 MCP，Claude 会问你：“好，我知道怎么分析了，但数据在哪儿呢？你得发给我。”
如果你只有 MCP（连上了库），但没有 Skill，Claude 会说：“好，我看到成千上万条数据了，然后呢？你想让我干嘛？”
所以，最高级的高手，是把 MCP + Skills 结合起来用：用 MCP 自动抓取数据，用 Skills 自动处理数据。
说了这么多概念，我们最后把它们全部串起来，看看到底能产生多大的威力。
在文章的最后，Claude 官方给出了一个终极示例：构建一个竞争情报分析智能体（Competitive Analysis Agent）。
如果你想做一份深度的竞品调研，只靠现在的你和一个聊天框，你需要手动去搜集资料、手动喂给 AI、手动调整它的输出，大概要花好几天。
现在，利用我们今天讲的所有工具，我们可以搭建一套自动化的流水线：
第一步：搭建地基（Projects）
创建一个叫“竞争情报”的 Project。
往里面上传过去所有的市场分析报告、竞品的产品文档、从 CRM 导出的一堆客户反馈。
在 Project 的自定义指令里写上战略目标：“我们要从产品差异化的角度去分析对手，寻找市场空白点。”
（这就给了 AI 一个持久的背景环境。）
第二步：打通数据（MCP）
开启 MCP 服务，连接公司的 Google Drive（这样可以读取同事们共享的最新文档），连接 GitHub（这样可以监视竞品的开源代码动态）。
（这就给了 AI 实时的外部视野。）
第三步：注入灵魂（Skills）
如果你们公司有一套独特的“SWOT 分析法”或者“五力模型分析规范”，把它做成一个 Skill。
教它：“看到竞品动态时，必须按‘威胁等级’、‘影响范围’、‘应对策略’这三步来分析。”
（这就给了 AI 专业的办事方法。）
第四步：组建团队（Subagents）
你可能会发现，分析几千条 GitHub 代码更新太累了，而且容易干扰主线任务。
于是你设计一个“技术侦探”子智能体。主智能体负责写总报告，但遇到技术细节时，就把任务派发给“技术侦探”。
这个侦探只负责看代码，看完后告诉主智能体：“嘿，我发现他们在最新的代码里增加了一个‘云同步’功能的接口，这可能是他们下一步的大动作。”
（这就实现了高效的分工协作。）
第五步：日常指挥（Prompts）
万事俱备。现在，作为老板的你，只需要在对话框里输入一句简单的提示词：
“帮我看看竞争对手 X 最近一个月在技术上有什么新动向，会对我们的 Q4 策略有什么影响？”
然后，神奇的事情发生了：
Claude（主智能体）在 Project 的背景知识下被唤醒，通过 MCP 抓取了最新的 GitHub 数据，把它扔给 Subagent 进行技术分析，拿回结果后，调用 Skill 里的分析方法论，最后生成了一份完全符合你心意的、格式完美的战略报告。
这一切，可能只需要几分钟。
听完这个案例，不知道大家是什么感觉？
我最大的感受是：我们正在经历从“和 AI 聊天”到“雇佣 AI 工作”的转变。
以前，我们把 Claude 当成一个博学的网友，有问题问它一下。
现在，通过 Projects、Skills、Subagents 和 MCP，我们其实是在编程。但我们不是用代码在编程，我们是用“工作流”在编程，是用我们的“管理智慧”在编程。
这篇文章给我们的启示是：不要被这些新名词吓倒。它们每一个的出现，都是为了模拟人类真实工作中的一个环节。
•   Prompts 是日常的口头指令。
•   Projects 是我们的档案室和办公室。
•   Skills 是员工培训手册。
•   Subagents 是专业的部门分工。
•   MCP 是连接互联网和公司内网的网线。
当你把它们对应到现实世界，一切就变得理所当然了。
所以，回到开头那个问题：如果你还在为“工具箱焦虑”而烦恼，我的建议是——从**Skills（技能）**开始尝试。
看看你手头最重复、最繁琐的那件事，能不能把它写成一个 Skill？一旦你迈出了这一步，你就会发现，你不再是一个人在战斗，你真的拥有了一位可以不断进化的数字员工。
