官方解构 Claude Agent SDK内核：Bash 与文件系统何以成为 AI 的底层基石？
过去的一年里，Anthropic 的 Claude Code 可以说是第一个真正意义上被广泛应用的 Agent 产品。它不仅能写代码，还能自主构建上下文、决策执行路径，甚至在长达数十分钟的交互中持续工作。基于构建与运营 Claude Code 的经验，Anthropic 推出了 Claude Agent SDK。这一套东西可不是一个简单的工具集，而是一套完整的、观点鲜明的 Agent 构建套件，里面封装了模型、工具、提示工程、文件系统交互、技能（Skills）和安全沙箱等核心组件。
今天我想分享一个来自 Thariq Shihipar 的官方技术分享。Thariq 是 Anthropic 的创始团队成员，也是 Claude Agent SDK 的核心负责人，他深度参与了 Claude Code 的开发。
那么，构建一个强大的 AI Agent 到底需要什么呢？Thariq 给出了一个非常有意思的答案：基于 Unix 基本元素的 Bash 工具和文件系统。
首先，让我们来聊聊 Anthropic 在构建 Agent 时非常独特的一个哲学，那就是——“Bash 即一切”。这与行业中普遍的“工具优先”思路有着明显的区别。
所以，Anthropic 认为，Bash 和文件系统等 Unix 基本元素其实是构建强大 Agent 最有效的工具。你想想看，传统的 Agent 框架通常会为每个功能——比如搜索啊、代码检查啊——都创建一个独立的工具。这种方法的问题在于，当工具数量变多时，上下文窗口会被大量占用，而且工具之间也很难组合。
相比之下，Claude Code 就聪明多了。它的强大之处在于它不依赖大量的预设工具，而是直接使用 grep 进行搜索，通过 npm run lint 执行代码检查。大家知道，Bash 的管道（pipe）、脚本编写，以及调用现有命令行软件（比如 ffmpeg、sqlite）的能力是非常强大的，这使得 Bash 成为一个通用且高度可组合的“元工具”，也就实现了所谓的“代码即工具”（Code as Tools）的理念。
还有一个听起来有点反直觉，但实际上特别强大的理念，就是利用代码生成（Code Generation）来完成非编码任务。当 Agent 面对一个需要调用多个 API、进行数据分析或者执行非结构化动作的请求时，它可以动态地编写并执行一段脚本——比如 Python 或 TypeScript——来完成任务。举个例子，如果要查询天气并提供穿衣建议，Agent 可以直接写一个脚本来调用天气 API，获取地理位置，甚至整合用户的衣橱 API，从而实现高度动态和灵活的逻辑组合。
了解了核心哲学，那么构建一个可靠的 Agent 需要遵循什么样的流程呢？这里有一个系统性的设计循环，强调了 Agent 在执行任务时的三个关键阶段。
第一步是收集上下文。这是 Agent 理解任务和环境的起点。比如在代码任务中，它会用 grep 或 ls 去查找相关文件；在邮件处理任务中，它会去搜索相关邮件。这一步的设计对 Agent 的最终表现有着决定性的影响，但也往往容易被开发者忽视。所以，如何设计高效的上下文收集接口，其实是一个充满创造性的工程挑战。
第二步是执行动作。在收集到足够的信息后，Agent 就会开始执行具体操作。执行动作的机制主要分为三种，选择哪一种通常取决于任务的特性：
具体来说，第一种是 工具（Tools）。这指的是那些结构化的、预定义的函数调用。它的优点非常明显：可靠、快速，而且错误率低。但是，它的缺点在于上下文占用比较高，而且比较死板，很难灵活组合。所以，它通常适用于那些原子性的、不可逆的操作，比如发送一封邮件，或者写入一个文件。
第二种是 Bash，也就是通过命令行接口来执行操作。它的优势在于高度可组合，而且对上下文的占用很低。不过，有时候 Agent 需要通过 --help 等方式来探索命令的用法，所以会有一定的延迟。这种机制非常适合那些需要组合多个步骤的灵活任务，比如进行代码检查或者文件搜索。
第三种则是 代码生成（Codegen），也就是动态生成并执行代码脚本。这是最灵活的一种方式，可以实现非常复杂的动态逻辑。当然，代价就是执行时间通常是最长的，因为涉及到编译和解释的过程。但当你需要进行复杂的 API 编排、深度数据分析，或者需要复用代码模式时，这绝对是最佳选择。
1.   验证工作 (Verify Work): 第三步，也是非常关键的一步，就是验证工作。这是确保 Agent 可靠性的关键环节。一个优秀的 Agent 设计必须包含验证机制。实际上，任务的可验证性强度，是判断其是否适合用 Agent 实现的重要标准。例如，代码生成任务可以通过代码检查器（linter）和编译器进行验证；研究类任务可以通过引用来源进行部分验证。验证可以是确定性的规则——比如检查空指针、文件读取前置检查，也可以是基于模型的——比如使用一个独立的“QA Agent”来进行审查。
除了这个核心循环，如果我们想要构建生产级的 Agent，还需要理解几个关键的架构组件。
首先是 安全与沙箱 (Security & Sandboxing)。赋予 Agent 执行 Bash 命令和访问文件系统的能力，自然会带来巨大的安全挑战。对此，Anthropic 提出了一个叫“瑞士奶酪防御”（Swiss Cheese Defense）的模型，意思就是通过多层防御来保障安全：
•   第一层是 模型层: 对模型进行对齐训练，让它本身就具备安全意识。
•   第二层是 套件层 (Harness): SDK 内置了 Bash 命令解析器和权限控制，防止恶意操作。
•   第三层是 环境层: 将 Agent 运行在隔离的沙箱容器中（比如 E2B 或 Modal），限制它的网络访问和文件系统操作范围，防止数据泄露。
接下来一个重要的概念是 技能与渐进式上下文披露 (Skills & Progressive Context Disclosure)。技能是 Anthropic 提出的一种高级上下文管理机制。它本质上是一个包含特定任务指南、代码示例和提示的文件集合，或者说文件夹。当 Agent 需要执行一项它不熟悉的复杂任务时——比如制作一份专业的前端设计稿——它可以主动查找并“学习”对应的技能。这是一种“渐进式上下文披露”模式，避免了一次性将所有信息都加载到提示中，而是让 Agent 按需获取专业知识。
此外还有 子 Agent (Sub-agents) 的概念。对于极其复杂的任务，我们可以将其分解，并派生出多个子 Agent 并行或串行处理。每个子 Agent 在独立的上下文中完成自己的子任务，然后只把最终结果返回给主 Agent。这种模式极大地优化了上下文管理，防止主 Agent 的思维过程被繁杂的中间步骤所“污染”。Claude Agent SDK 对子 Agent 的创建和管理提供了很好的支持。
聊完了架构，Thariq 还分享了一些非常有价值的 Agent 设计思维和原则。
这里他提到了一个很有趣的比喻，叫 Agent 的“React”时刻。
早期的 Web 开发追求的是直接和简单，但在构建大型应用时就会变得难以维护。React 的出现虽然带来了 JSX 语法、打包工具等额外的学习成本和配置复杂性，但它为构建大型、可维护的 Web 应用提供了坚实的基础。
Claude Agent SDK 现在正处于这样的时刻。它引入了沙箱环境、容器化以及文件系统管理。虽然这些配置增加了启动的门槛，相比直接在本地运行脚本显得繁琐了一些，但为了实现真正的安全性、隔离性和大规模部署，这种“必要的复杂性”是不可或缺的工程权衡。毕竟，如果不通过沙箱隔离，让 Agent 直接在用户主机上拥有最高权限，那可是极其危险的。
另一个重要的思维模型是 状态机思维，特别是为什么 Git 是 Agent 的完美环境。
在设计 Agent 的交互环境时，任务的“可逆性”决定了开发的难度。
•   比如说 高可逆性环境（像 Git）：代码编写之所以是 Agent 最擅长的领域之一，核心原因就在于 Git 提供了完美的时间旅行能力。如果 Agent 写错了代码，它可以执行回滚操作，状态就能完全恢复。这种容错机制让 Agent 能够大胆尝试并自我修正。
•   而 低可逆性环境（比如 UI 自动化） 就麻烦多了。Thariq 举了个“外卖点餐”的例子：如果 Agent 错误地把百事可乐加入了购物车，而用户想要的是可口可乐，它没法简单地“撤销”。它必须导航回购物车，删除错误商品，再重新添加。这种状态机的复杂性会随着步骤增加呈指数级上升。
所以，开发者应尽可能将任务环境设计为“可逆的”，或者在关键步骤设置“检查点”（Checkpoints），允许 Agent 在犯错后能够安全地回退到已知状态。
接下来我们看看如何 应对“百万行”数据的挑战，也就是草稿本模式。
当 Agent 需要处理 Excel 表格中数百万行数据或超大型代码库时，如果直接把所有内容都塞入上下文窗口，不仅昂贵，而且会导致模型性能下降。
解决方案是什么呢？就是模仿人类专家的行为模式：
1.   首先是 分层检索：先读取表头或目录，了解数据结构。
2.   然后 按需搜索：使用 grep 或 SQL 查询特定的关键词（比如“2026年收入”），只获取相关的切片。
3.   最后利用 草稿本（Scratchpad）：建立一个独立的“草稿文件”。Agent 应该把搜索到的关键信息、中间计算结果写入这个文件，而不是试图在“大脑”里记住所有细节。
这种方法让 Agent 能够处理远超其上下文限制的海量数据。
还有一个原则是 持续验证：在每一个环节植入确定性规则。
“验证”不应该只发生在任务结束的时候。高效的 Agent 系统会在执行过程中插入大量的确定性检查（Hooks）。例如，Claude Code 内部有一条硬性规则：如果 Agent 试图修改一个它还没有读取过的文件，系统会直接拦截并报错，提示它必须先读取文件内容。这种基于规则的启发式检查比单纯依赖模型的自我反思要更加可靠，也更高效。通过在 SDK 中注册 Hooks，开发者可以在任何工具调用前后插入自定义的检查逻辑。
大家可能会好奇，多个 Agent 之间该如何协作和通信呢？ Thariq 认为其实不需要发明新的复杂协议。Agent 本质上就是软件程序，它们应当使用现有的互联网标准进行交流，也就是 HTTP 请求、API 调用和文件共享。未来的多 Agent 系统可能不需要全新的语言，它们会像现在的微服务架构一样，通过标准的接口进行交互。有些开发者甚至尝试建立虚拟的论坛，让不同的 Agent 在其中发帖和回复来交换信息，这种基于文本的自然交流已经被证明是有效的。
说到这儿，你可能会问，那我们在 开发 Agent 原型的时候，有什么最佳实践吗？ 在演示构建“宝可梦（Pokémon）组队助手”时，Thariq 展示了一个相当颠覆性的开发流程：
•   在 传统模式 下：开发者需要手动阅读 API 文档，手动编写 Python 或 TypeScript 包装器，然后定义工具给 Agent 使用。
•   而在 Agent 优先模式 下：你可以直接命令 Claude Code 去阅读在线文档，并让它“为这个 API 生成一个 TypeScript SDK 库”。
Thariq 推荐的原型设计流程是这样的：
1.   从 Claude Code 开始：不要一上来就从零开始编写 Agent 框架。直接打开 Claude Code，把它作为一个理想的 Agent 执行环境。
2.   提供物料：把你的 API 文档、需要调用的脚本、以及描述任务目标和可用资源的 claude.md 文件提供给 Claude Code。
3.   下达指令并观察：让 Claude Code 去执行你的任务。
4.   阅读“日志”：仔细观察 Agent 的每一步思考和行动。分析它在哪里遇到了困难，在哪里做出了错误决策。
5.   迭代优化：根据观察结果，调整你提供的 API 设计、脚本功能或 claude.md 中的说明，然后重复这个过程。这个循环能帮助你快速发现并解决特定领域的核心挑战。
通过这种方式，开发者可以将精力集中在“Agentic Search Interface”设计、数据预处理和验证逻辑等高价值问题上，而不是耗费在底层框架的搭建上。
在分享的最后，Thariq 给开发者们提了一个特别诚恳的建议。
他强调说，AI 领域的变化速度极快。现在的最佳实践——比如通过文件系统管理上下文——在六个月后可能就会过时。
好了,今天的分享就到这里,更多精彩内容欢迎在小宇宙平台订阅AI智识录,持续了解学习AI科技领域的经典智识。
所以，开发者应当关注“今天有效”的技术，利用当前模型的优势快速构建产品并抢占市场。千万不要为了追求完美的未来架构而停滞不前。要有勇气在六个月后扔掉现在的代码并重写，因为这正是初创团队相对于大公司最大的竞争优势——极速的迭代与重构能力。
